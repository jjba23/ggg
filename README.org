* What is this black magic? 🪄

Through SVG generation from Lisp (Guile Scheme) we leverage a beautiful DSL (Domain-Specific Language) and apply some mathematical knowledge to build pixel perfect badges.

The SVG (Scalable Vector Graphics) can then be easily converted without quality loss to any desired format. Create your badges programatically with a polished aesthetic!

-  Scheme Powered :: Built with the expressive and functional Guile Scheme, ensuring a concise and maintainable codebase.
-  Vector Graphics (SVG) :: Generates crisp and scalable SVG images, perfect for any screen resolution.
-  Raster Images (PNG) :: Also produces PNG versions for broader compatibility.
-  Highly Customizable :: Customize the text, background colors, text colors, logos, etc.
-  Per-Glyph Styles :: Pick a finish per badge: flat, square, shadow, plastic, frosted glass, material, Frutiger Aero or neon. Styles change the look, never the layout.
-  Theme Colors :: Every color of Catppuccin (mocha, macchiato, frappé, latte), Doom (~doom-one~, ~doom-one-light~), Dracula (~dracula~, ~dracula-alucard~), Solarized (dark, light) and Modus (~modus-operandi~, ~modus-vivendi~) is available as a named color such as ~catppuccin-mocha-red~, instead of raw hex codes.
-  Full SVG Logos :: Save logos as complete ~<svg>~ elements, allowing multiple paths, groups and gradients.
-  Logo Library :: Ships hundreds of ready-to-use logos, browsable in a generated gallery page.
-  Helpful Errors :: Invalid glyph files are reported with actionable messages before anything is generated.
-  Simple Definition :: Badge configurations are defined in an easy-to-understand data structure within the Scheme code.

Badges follow the compact geometry of the badges GitHub shows: 20px tall, 11px text, a 14px logo, 5px of padding on each side of a text run and 3px rounded corners -- all drawn 9.18% larger (6%, then a further 3%), so a default badge is 21.84px tall with 12.01px text and a 15.29px logo, which reads a little better next to body text. ggg estimates text width by summing a per-character width for the font size (capitals, digits and wide letters take more room than narrow ones) and adding that padding, so a badge stays as tight as the ones you see in README files.

ggg tries to provide sensible defaults to every option, but allow customization. We construct the SVG structure using SXML (S-expressions representing XML). This makes it easy to define the SVG elements and their attributes programmatically.

We choose for ~geometricPrecision~ in SVG to allow highest quality and fidelity, to prioritize geometric accuracy over rendering speed. This is often desirable for crisp, clean vector graphics like badges. In essence, the "magic" lies in the combination of:

- Data-driven generation :: The badge is created based on the input data.
- Precise calculations :: The dimensions and positions of elements are precisely calculated to achieve the desired layout.
- Using SVG effectively :: Standard SVG elements and attributes are used in a structured way to create the visual appearance.
- Abstraction :: of layout and view thanks to Lisp, handling all options gracefully.

* How to define a glyph?

The module where you define your glyphs should be ~(ggg config)~ as that is used to read config dynamically from. See ~glyphs/jjba23.scm~ for an example.

#+begin_src scheme
(define-module (ggg config)
  #:declarative? #t)
#+end_src

Defining your glyphs is simple and only requires very basic knowledge of Lisp/Scheme:

#+begin_src scheme
(define my-scheme-guile-glyph
  `((sections ((background . catppuccin-mocha-surface2) (text . "Scheme")
               (color . catppuccin-mocha-text)
               (logo . lambda))
              ((background . catppuccin-mocha-peach) (text . "Guile")
               (color . catppuccin-mocha-base)))
    (id . scheme-guile)))

#+end_src

A glyph can have any number of sections, not just the two shown above: each section becomes one segment with its own text, background and text color, and the badge grows to fit them. A ~logo~ belongs to the first section; the remaining sections are text only. A glyph can also pick a ~style~ (see [[*Styles][Styles]]) or override its ~border-radius~ and ~height~.

Then to ensure that ggg will read your glyphs from the file, you need to export them in the ~ggg-glyphs~ list:

#+begin_src scheme
(define ggg-glyphs
  (list my-scheme-guile-glyph))
#+end_src

** Colors

Backgrounds and text colors are names taken from the palettes of five theme families, or raw hex strings (e.g. ~"#555"~) for one-off colors. Every name is qualified with its theme, so it always means the same thing: ~<theme>-<color>~.

#+begin_src scheme
(background . catppuccin-mocha-surface2) ;; #585b70, the neutral first-section background
(background . catppuccin-mocha-yellow)   ;; #f9e2af
(background . catppuccin-mocha-pink)     ;; #f5c2e7
(color . catppuccin-mocha-text)          ;; #cdd6f4
#+end_src

| Theme family | Themes                                                                               |
|--------------+--------------------------------------------------------------------------------------|
| Catppuccin   | ~catppuccin-mocha~, ~catppuccin-macchiato~, ~catppuccin-frappe~, ~catppuccin-latte~   |
| Doom         | ~doom-one~, ~doom-one-light~                                                         |
| Dracula      | ~dracula~, ~dracula-alucard~                                                         |
| Solarized    | ~solarized-dark~, ~solarized-light~                                                  |
| Modus        | ~modus-operandi~, ~modus-vivendi~                                                    |

Each theme keeps its own color vocabulary, so names feel native to the theme you picked:

- Catppuccin :: ~rosewater~, ~flamingo~, ~pink~, ~mauve~, ~red~, ~maroon~, ~peach~, ~yellow~, ~green~, ~teal~, ~sky~, ~sapphire~, ~blue~, ~lavender~, plus the shades ~text~, ~subtext1~, ~subtext0~, ~overlay2~, ~overlay1~, ~overlay0~, ~surface2~, ~surface1~, ~surface0~, ~base~, ~mantle~, ~crust~.
- Doom :: ~bg~, ~bg-alt~, ~base0~ to ~base8~, ~fg~, ~fg-alt~, ~grey~, ~red~, ~orange~, ~green~, ~teal~, ~yellow~, ~blue~, ~dark-blue~, ~magenta~, ~violet~, ~cyan~, ~dark-cyan~.
- Dracula :: ~background~, ~current-line~, ~foreground~, ~comment~, ~cyan~, ~green~, ~orange~, ~pink~, ~purple~, ~red~, ~yellow~.
- Solarized :: ~base03~ to ~base3~, ~yellow~, ~orange~, ~red~, ~magenta~, ~violet~, ~blue~, ~cyan~, ~green~.
- Modus :: ~bg-main~, ~bg-dim~, ~bg-active~, ~bg-inactive~, ~fg-main~, ~fg-dim~, ~fg-active~, ~fg-alt~, ~red~, ~green~, ~yellow~, ~blue~, ~magenta~, ~cyan~.

Run ~ggg --list-colors~ to print every name (236 of them) with its hex value, grouped by theme. Hex strings keep working and are still validated, so ~"#ggg"~ or ~"#12345"~ are rejected with a message instead of producing a broken badge.

A practical note on contrast: Catppuccin accents range from light pastels (mocha) to mid-tone and deep shades (latte), so the ink has to follow the background. Pick whichever light or dark shade gives the strongest contrast -- for example ~base~ on a deep accent, a near-black on a pale one -- and let the ratio decide rather than the name of the color. Every section of the shipped glyph files reaches at least 4.5:1 (WCAG AA for normal text), and the test suite enforces that, so ~maak test~ catches a badge whose text becomes hard to read.

** Styles

A glyph can pick a visual finish with an optional ~style~ setting. Styles decorate the badge without moving its layout: the sections, the logo and the text stay exactly where they are.

#+begin_src scheme
(define my-neon-glyph
  `((sections ((background . catppuccin-mocha-surface2) (text . "Scheme")
               (color . catppuccin-mocha-text)
               (logo . lambda))
              ((background . catppuccin-mocha-mauve) (text . "Guile")
               (color . catppuccin-mocha-base)))
    (id . scheme-guile-neon)
    (style . neon)))
#+end_src

| Style           | What it looks like                                                  |
|-----------------+---------------------------------------------------------------------|
| ~flat~          | the default: flat colors and the usual rounded corners              |
| ~square~        | sharp, square corners                                               |
| ~shadow~        | a subtle shadow just under the content, with no size change         |
| ~plastic~       | a glossy highlight on the top half and a bright inner bevel         |
| ~frosted-glass~ | a translucent frost sheen behind a light hairline border            |
| ~material~      | a Material-style sheen with a soft elevation shade                  |
| ~frutiger~      | glossy Frutiger Aero glass, with a sky tint and a bright reflection |
| ~neon~          | a dark plate with crisp glowing outlines and bright text            |

The setting is optional and defaults to ~flat~, so existing glyph files keep their look. Style names are forgiving: ~(style . "frosted glass")~, ~(style . frosted_glass)~ and ~(style . glass)~ all mean ~frosted-glass~. Run ~ggg --list-styles~ to print the table above, and see every finish side by side in the [[./test/gallery.html][gallery]].

Every style keeps exactly the same canvas, width and height as ~flat~, so a row of badges that mix styles always lines up. Shadows, glosses and glows are painted inside the badge, never around it. The style badges at the top of this README are the ~Styles~ group of ~glyphs/showcase.scm~, one badge per finish.

** Logos

Logos are full SVG documents stored as ~resources/logos/<name>.svg~ and are referenced by name:

#+begin_src scheme
(sections ((background . catppuccin-mocha-surface2)
           (text . "Project")
           (color . catppuccin-mocha-text)
           (logo . sparkle)))
#+end_src

Because the whole ~<svg>~ element is kept, a logo can use as many paths, groups, gradients, transforms or filters as it needs. Only the outer ~<svg>~ element has to provide a ~viewBox~ (so ggg can scale the logo to the badge height); width, height, x and y are managed by ggg. Editor metadata such as the ~inkscape~ or ~sodipodi~ namespaces is dropped when the logo is inlined.

#+begin_src xml
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 24 24">
  <defs>
    <linearGradient id="sparkle-gradient" x1="0" y1="0" x2="1" y2="1">
      <stop offset="0" stop-color="#fff"/>
      <stop offset="1" stop-color="#80aadf"/>
    </linearGradient>
  </defs>
  <path fill="url(#sparkle-gradient)" d="M12 2 2 12h6v10h8V12h6z"/>
  <circle cx="18" cy="6" r="3" fill="#fff"/>
</svg>
#+end_src

A logo is a single SVG document, so there is nothing else to configure: give the file a ~viewBox~ and ggg scales and places it inside the badge.

*** The logo library

ggg ships several hundred logos, so most badges can be written without drawing anything:

- the original ggg logos (GNU, Guix, Emacs, Rust, Scala, ...),
- a curated set of tech logos from the [[https://simpleicons.org/][Simple Icons]] collection (CC0-1.0), covering languages, frameworks, databases, editors, distributions, cloud providers, CI systems and more,
- hand-authored logos such as ~ggg~, ~ggg-warm~, ~sparkle~, ~flame~, ~planet~, ~leaf~, ~shield-check~, ~database-stack~, ~terminal-prompt~, ~atom-orbit~, ~compass~, ~anchor~, ~bolt~ and ~heart~ that show gradients, groups and multi-shape drawings.

[[./CREDITS.org][CREDITS.org]] lists every logo with where it comes from and its license, and notes which brand marks were deliberately left out because their upstream license is not a free one.

One entry deserves a note. ~java.svg~ is the Java coffee-cup mark, Oracle's trademark. Simple Icons used to ship it and removed it in 2022 after Oracle asked for its removal; ggg keeps the cup as a nominative reference to Java, which is why the credits call it out separately from the other logos.

** Browsing badges, colors and logos

Run ~ggg --list-logos~ for the names, or generate the gallery, a single self-contained HTML page that renders every badge of your glyph files at its real size, inlines every logo with its name and the snippet to use, and shows every named color of every theme as a copyable swatch:

#+begin_src shell
ggg --gallery ./test/gallery.html --glyphs ./glyphs
#+end_src

~--glyphs~ takes a glyph file or a directory of ~.scm~ files; the gallery groups the badges by file. Click the snippet under any badge or logo to copy its definition to the clipboard, or click a color swatch to copy its qualified name (such as ~catppuccin-mocha-red~) to paste into a glyph. Without ~--glyphs~ you still get the color palettes and the logo library. [[./test/gallery.html][test/gallery.html]] is that page, and ~maak gallery~ regenerates it, so it always matches the glyphs in ~glyphs/~, the colors in ~src/ggg/colors.scm~ and the logos in ~resources/logos/~.

~maak deploy~ (the task the Woodpecker/Byggsteg job runs on every push) writes the same page to ~dist/gallery.html~. The deployed gallery is at [[https://jointhefreeworld.org/ggg/dist/gallery.html][jointhefreeworld.org/ggg/dist/gallery.html]].

** The badge showcase

~glyphs/showcase.scm~ ships one ready-made badge per popular logo in the library, grouped by what the project is (languages, web frameworks and APIs, databases and queues, infrastructure, security and networking, cloud, git, observability, distributions, editors, shells, AI, testing, media, chat). It closes with a ~Theme variants~ group that paints one badge per palette and a ~Styles~ group that shows every badge style: 177 badges in all. Every badge reads ~<logo> Name | category~. Its label stays Catppuccin mocha so the library reads alike, while the second section takes the accent closest to the project's own hue (blue stays ~blue~, orange becomes ~peach~, black brands use the neutral ~overlay2~) and draws its text in ~base~.

#+begin_src scheme
(define glyph-postgresql
  (badge 'postgresql "PostgreSQL" 'postgresql "database" 'blue))

;; ... and the same helper pointed at another palette, with the color that
;; reads on that theme's accents:
(define glyph-theme-dracula
  (badge 'theme-dracula "Dracula" 'paint "dracula" 'purple
         #:theme 'dracula #:ink 'background))

;; ... and a styled badge, from the Styles group:
(define glyph-style-neon
  (styled-badge 'style-neon "Neon" 'atom-orbit "glow" 'red 'neon))
#+end_src

So the second sections of the showcase mix all five theme families: ~mocha~, ~macchiato~, ~frappe~, ~latte~, ~doom-one~, ~doom-one-light~, ~dracula~, ~alucard~, ~solarized~ dark and light, and ~modus~ operandi and vivendi can be compared side by side. The ~badge~ helper qualifies each accent with its theme, so nothing depends on which palette happens to be the default, and ~styled-badge~ adds a ~style~ to it.

~glyphs/jjba23.scm~ is the other half of the pair: 68 badges for the things a project ticks off one by one -- language and tool versions (~lang-python~, ~lang-go~, ~haskell-ghc910~, ~rust-185+~), build and package tooling (~build-cmake~, ~build-meson~, ~pkg-homebrew~), CI (~ci-buildkite~, ~ci-drone~, ~pipeline-succeeded~), tests, linting and formatting (~test-jest~, ~test-pytest~, ~lint-eslint~, ~fmt-prettier~), data and deployment (~db-postgresql~, ~db-redis~, ~deploy-kubernetes~, ~infra-terraform~), shells, editors, licenses, and the project badges of the tools ggg is built with. They pair a darker Catppuccin latte label with Catppuccin mocha's pastel accents: the logo side is a ~subtext1~ gray with near-white ~base~ text (5.5:1 contrast), and every accent is a soft mocha pastel with the dark ~mocha-base~ ink (7:1 or better). Hues follow the projects: Java, Scala and Redis stay red, Scheme and Guile are orange, Guix and Homebrew are yellow, licenses and most databases are blue, Go is sky, Rust is orange, Emacs is pink -- so the set reads warmer and friendlier without losing contrast. Every badge in the set also wears the subtle ~shadow~ style.

Both files are part of ~dist/~, and the gallery shows them next to each other. Because ggg clears its destination directory, the second file has to be rendered with ~-k~ / ~--keep~:

#+begin_src shell
maak run            # renders both glyph files into ./dist
maak run-convert    # ... and also writes a PNG next to each SVG
maak showcase       # renders only the showcase into ./dist
#+end_src

Use this file as a starting point: copy the badge you need into your own glyph file, or point ggg at it directly with ~ggg -f ./glyphs/showcase.scm -d ./dist -k -c~.

** Adding a logo

Drop a full SVG document into ~resources/logos/<name>.svg~ and reference it with ~(logo . name)~. Only the ~<svg>~ element and its ~viewBox~ are required; ~title~ elements are picked up by the gallery as the logo's display name. Please also add a line to [[./CREDITS.org][CREDITS.org]] with the source and license of the logo.

Older projects may still have the removed ~resources/svg-paths/~ directory, which held only the data of a path's ~d~ attribute. It is not read anymore, and ggg stops with an explanation and the list of files if it finds one: wrap each file in an SVG document at ~resources/logos/<name>.svg~.

** Validation and errors

Before generating anything, ggg validates your whole glyph file and reports *every* problem it finds, with a hint on how to fix it: unknown color, logo or style names (with a suggestion when a name is close), missing ~text~, sections without colors, malformed ~(key value)~ pairs that should be ~(key . value)~, duplicate or unusable glyph ~id~s, and so on. Nothing is written to the destination directory when the configuration is invalid.

* Help

The project's automation is done using [[https://codeberg.org/jjba23/maak][Maak]] , check the ~maak.scm~ file.

Also, find the technical Guile Scheme API documentation for GGG here:

https://jointhefreeworld.org/api-docs/ggg/API.html

You can see the program's help by invoking it with the ~--help~ argument or looking at ~resources/help.txt~.

Useful helpers while working on glyphs:

- ~ggg --list-colors~ :: list every theme color available to glyph files, grouped by theme.
- ~ggg --list-logos~ :: list the logos found in the resources directory.
- ~ggg --list-styles~ :: list the badge styles (flat, square, shadow, plastic, frosted-glass, material, frutiger, neon) and what each one looks like.
- ~ggg --gallery FILE [--glyphs PATH]~ :: write an HTML gallery of every badge, color palette and logo (see [[./test/gallery.html][test/gallery.html]]).
- ~ggg -k~ / ~--keep~ :: render a second glyph file into a destination directory without clearing it first.
- ~ggg -V~ / ~--version~ :: print the version, license and homepage.
- ~maak showcase~ :: regenerate the popular-logo badges of [[./glyphs/showcase.scm][glyphs/showcase.scm]] in ~dist/~.
- ~maak test~ (or ~guile -L ./src ./test/ggg-tests.scm~) :: run the test suite, which covers color resolution, the logo library, glyph validation and the gallery.
- ~maak release~ :: sync, commit and tag a release (see below).

** Releasing

The version lives in one place, ~src/ggg/version.scm~: that is what ~ggg --version~ prints, what ~default.nix~ reads while it evaluates the derivation, and what ~maak version~ shows. Bump it, then let Maak do the rest:

#+begin_src shell
# edit src/ggg/version.scm: (define ggg-version "0.11.0")
maak release
#+end_src

~maak release~ writes that version into ~guix.scm~ (the one file that cannot read a Scheme module), commits everything tracked as ~chore: Release vX.Y.Z~, and tags the commit. It refuses to re-release a version whose tag already exists, and tags the current commit when there is nothing left to commit. Render the badges first (~maak run~, ~maak gallery~) if the glyph files changed, so the release commit carries the images it describes.

** On Guix

 You can alternatively choose to download it from source, useful for developing it or customizing it. In that case you'll need:

- *Guix*: The Guix package manager will ensure a reproducible working software, and will manage all needed dependencies for you.
-  *Guile Scheme:*  This entire program is written using the official GNU extension language, Guile Scheme.
-  *ImageMagick:* If you want to generate PNG files, you'll need ImageMagick (specifically the ~convert~ command). If ImageMagick cannot read SVG files (some distributions disable that in its security policy), ggg falls back to *Inkscape*.

Check the ~maak.scm~, ~Makefile~ and the ~guix.scm~ and ~manifest.scm~ for more details.

For example, to enter an environment shell with ggg temporarily you can use:
#+begin_src shell
guix shell -f guix.scm
#+end_src

You can also chain commands to it:
#+begin_src shell
guix shell -f guix.scm -- ggg --help
#+end_src

ggg offers a ~--help~ / ~-h~ flag which will explain all options (also visible in ~resources/help.txt~). You should point ggg to the path to your configuration file:

#+begin_src shell
ggg --file ./glyphs/jjba23.scm --destination ./dist
#+end_src

** On Podman/Docker

ggg is also available as a Docker container, from DockerHub (also compatible with Podman).

https://hub.docker.com/repository/docker/jjba23/ggg/general

You can also build images of ggg yourself, using ~guix pack~. See the ~maak.scm~ file for more.
To load these tarball images, you can do ~podman load < my.tar.gz~

You can run ggg from the container, and bind your local filesystem to give access, for example:

#+begin_src shell
 docker container run -v /home/joe:/home/joe \
     docker.io/jjba23/ggg:latest ggg --file /home/joe/glyphs.scm --destination ./dist
#+end_src

** On Nix

~ggg~ also is packaged via Nix.

#+begin_src shell
# Building via legacy Nix
nix-build default.nix

# Testing the result
./result/bin/ggg --help

# Building via Nix Flakes
nix build
./result/bin/ggg --file ./glyphs/jjba23.scm -d ./dist
#+end_src

** On Debian, openSUSE and Arch

The source tree carries the packaging for the distributions that Guix, Nix and
the container image do not cover:

- ~packaging/debian~ :: debhelper packaging, built with ~dpkg-buildpackage~.
- ~packaging/opensuse~ :: a spec file for ~rpmbuild~, plus the OBS ~_service~
  that fetches the sources from Codeberg.
- ~packaging/arch~ :: a ~PKGBUILD~, built with ~makepkg~.

The three install the same layout -- ~/usr/bin/ggg~, the Scheme modules under
~/usr/share/guile/site/3.0/ggg~, their byte-compiled copies in the
interpreter's ~site-ccache~ directory, and the help text and logo library under
~/usr/share/ggg/resources~ -- which is the layout ~scripts/ggg~ resolves
relative to its own prefix at runtime.

#+begin_src shell
# Debian/Ubuntu: the debian/ directory belongs at the top of the source tree
cp -r packaging/debian debian
dpkg-buildpackage -us -uc -b

# openSUSE, from a tarball unpacked as ggg-0.16.0
rpmbuild -ba packaging/opensuse/ggg.spec

# Arch
cd packaging/arch && makepkg -si
#+end_src

See [[./packaging/FOLLOW-UP-PLAN.org][packaging/FOLLOW-UP-PLAN.org]] for what is still missing before each of them
can be submitted to the distributions.

* REPL: Interactive workflow, developer power

A REPL (Read-Eval-Print Loop) is an interactive environment, which can be used connected to your console, running application, language compiler and more, which gives you superpowers as an engineer 🦸🏼.

Lisp dialects, more specifically Guile Scheme, have great support for this. I personally of course like to do this with [[https://guix.gnu.org/][Guix]], [[https://www.gnu.org/software/emacs/][Emacs]], ([[https://git.sr.ht/~abcdw/emacs-arei][Arei/Ares]] + [[https://github.com/vspinu/sesman][sesman]]) you can get an ultimate extensible powerful editor experience, miles ahead of traditional IDEs 🐂 .

It fundamentally changes the development workflow by eliminating the slow /edit, save, compile, run/ cycle. Instead of writing a whole program and then running it to see what happens, you get a fast, conversational workflow. What does this mean for in practice?

- *Incremental Development:* Write, test, inspect, evaluate one function or even one line at a time. Get immediate feedback without running the entire app.
- *Powerful Debugging:* Forget adding ~print~ statements and restarting. You can pause, inspect objects, change values, and even redefine a broken function on the fly to test a fix in any environment (yes even in production, while running).
- *Fast Prototyping & Learning:* Instantly experiment with a new library or API. Just load it and start calling functions to see how they work, which is much faster than only reading documentation.

When integrated into your code editor, you can execute any piece of code (a line, a selection, or a file) with a keyboard shortcut and see the result instantly, creating a seamless and powerful development experience.

* On reproducibility: why GNU Guix?

A build should never fail because "it worked on my machine." Reliable software development requires explicit, bit-for-bit reproducibility and a functional approach to package management and system deployment.

[[https://jointhefreeworld.org/ggg/dist/gnu-guix.svg]]

- *Declarative build graphs.* Packages are pure functions of their inputs, with no implicit system state.
- *Programmable with Guile.* Full system and package configurations in [[https://www.gnu.org/software/guile/][Guile Scheme]] rather than rigid DSLs or static files.
- *Time travel.* Rebuild the exact system state from any point in git history with ~guix time-machine~.
- *Atomic operations.* Upgrade or roll back environments without orphaned dependencies or broken states.
- *Unified tooling.* One tool manages development shells, isolated containers, package builds and full system configurations.

maak inherits all of that for free, because a Maak file is just another Scheme file that Guix can evaluate — and because the same pin in ~channels.scm~ can drive the shell, the tests and the release. The pin is also readable from a task: ~guix-build~ and ~guix-program~ turn it into a store path and a program to run, which is what ~guix time-machine~ would otherwise have to be started for.
